## Phase 1: Scoping ✅

### ❓→✅ Discovery (exploration-first, answered from PRD/BRD/code rather than a live interview)

No live user was present to interview, so this section answers the exploration-first Phase 1 questions directly from the approved PRD/BRD and the code, with the evidence cited:

1. **What does the system do, and who depends on it?** The Cold Chain Monitor watches refrigerated display cases across Zava's grocery stores (5-store pilot today, ~400-store production target within 12 months per BRD CON-001). It raises alarms on temperature breaches, escalates unacknowledged alarms to on-call staff, accepts remote commands (setpoint/defrost) from technicians and a refrigeration vendor's remote service, and runs a store assistant that answers staff questions about whether stock is safe to sell. Night cover staff, refrigeration technicians, regional IT, the food-safety officer, and a third-party vendor all depend on it; ultimately so do shoppers and (implicitly, per BRD risk framing) a food-safety/recall exposure surface with no confirmed regulator voice (BRD A-9).
2. **What would be the worst outcome if it failed or was compromised?** The BRD's own evidence: a `silent-night`-class incident costs €260,411 pilot-region / €20.8M at 400-store scale, with 29 of 35 affected freezer cases found only by staff at opening, 234+ minutes after the breach began, while the assistant gave a reassuring answer. The worst case is a sustained, undetected cold-chain breach that reaches a shopper, triggers a recall, and was actively vouched for as "safe" by the assistant or silently went unescalated because of a stale pager contact.
3. **What is the organization most worried about right now?** Per the PRD's own handoff section: the authentication mechanism for commands/vendor sessions (explicitly deferred, FR-006/FR-009/NFR-004), the shared vendor account under a "won't fix" contract constraint (CON-002/ZFW-203), and — per the RAI handoff — the assistant's safety-adjacent answers and the people with no named owner since 2021/2024.
4. **Concrete surfaces surfaced by the user's own language (PRD/BRD), before naming frameworks:** "the command service," "the vendor remote-access channel," "fleet commands," "technician and vendor notes," "the pager contact list," "the ownership register," "the Night Gauntlet evidence harness." These map directly onto the bucket classification in Phase 2.

### Technology inventory and deployment

* **Stack:** Python 3.9, standard library only (`http.server.ThreadingHTTPServer`, in-memory `dataclasses`, no database, no external packages — CON-004). Server-Sent Events for the live feed. Static HTML/CSS/JS dashboard served from the same process.
* **Deployment model (today vs. production target):** Today, a single process bound to `127.0.0.1` only, reachable from one host (README.md, `server.py` docstring: "Binds to 127.0.0.1 only. There is no sign-in: being local is the only access control."). The PRD/BRD describe a production target of a distributed, store-network-reachable service across ~400 locations within 12 months. **This plan threat-models the production target the PRD describes**, per this session's operating instruction, while flagging every place the current code's security posture would not survive that transition unchanged.
* **Data processed:** Case temperature telemetry, alarm/incident/command audit records, technician and vendor free-text notes, a pager/escalation contact roster, an ownership register, and (in production) named-individual authentication/session records plus a recall-cost financial model (`data/business.json`).

## Phase 2: Bucket Analysis ✅

Components classified into the seven operational buckets plus the cross-cutting GS overlay, per `references/operational-buckets.md`. `ai-ml` is included because `raiEnabled` is `true`.

### identity/auth

**Components:** Command service identity model (FR-006/FR-007/FR-009 target design — not yet implemented); today's compensating control is host/origin checking only (`server.py` `_host_ok`, `_same_origin`); the vendor's single shared `svc-vendor` account (`roster.json` "Vendor remote access" owner comment; `simulator.py` `vendor_session`).

**Data flows:**
* Inbound: command requests from the dashboard (`/api/commands`), scripted/vendor command events (`simulator.py` `_command`), vendor session open/close events (`_apply_event` `vendor_session`) — all currently unauthenticated beyond host/origin checks.
* Outbound: applied commands reach case controllers (`commands.apply` → `_set_mode`, `setpoint`), with no identity attached to the applied command.

**Integration points:** Connects to `web/UI/reporting` (the `/api/commands`, `/api/board` endpoints), `infra` (case controllers), and `devops/platform-ops` (fleet-command ownership, currently vacant since 2021).

**Existing security controls:** None at the individual-identity level. Host/Origin checks exist (good compensating control for cross-origin web attacks, not a substitute for authentication).

**Identified gaps:** No sign-in (ZFW-305, "won't fix"); shared vendor account (ZFW-203, "won't fix"); command history cannot identify the sender (ZFW-246, open, high severity); no fleet-command approval hold; no vendor session time-boxing enforced server-side.

### web/UI/reporting

**Components:** `zava_cold_chain/server.py` — dashboard, JSON API (`/api/*`), SSE live feed (`/api/stream`), static asset serving.

**Data flows:**
* Inbound: all dashboard reads/writes arrive as HTTP GET/POST against `127.0.0.1` (today) or the store network (production target).
* Internal: routes dispatch into `business`, `ops`, `assistant`, `commands`, `gauntlet`, `impact`, `notify` modules while holding `sim.lock`.
* Outbound: JSON responses; SSE event stream pushes the live feed and clock ticks to any connected client.

**Integration points:** Front door for every other bucket — identity/auth (commands, board decisions), data (audit, case detail, business model), ai-ml (`/api/ask`, `/api/discard`), messaging (notify-contacts, alarms).

**Existing security controls:** `Host` header allow-list (`_host_ok`), `Origin`/`Content-Type` check for POST (`_same_origin`), a reasonable `Content-Security-Policy` and security-header set (`SECURITY_HEADERS`), path-traversal guard on static file serving (`_static`), `Cache-Control: no-store` on API responses, constant-rejection of `Infinity`/`NaN` JSON literals (`_reject_constant`).

**Identified gaps:** No authentication layer at all (ZFW-305); no per-route authorization/role separation (every reader sees audit, business-cost, and command surfaces alike); no request-rate or connection-count limiting on `/api/stream` or POST routes.

### data

**Components:** In-memory `Store` (command log, alarm records, notes, readings — defined in `zava_cold_chain/store.py`, referenced throughout `simulator.py`); ownership register (`data/roster.json` "owners"); recall-cost financial model (`data/business.json`, read by `business.py`).

**Data flows:**
* Inbound: readings and audit entries are appended on every simulated tick (`World.tick` → `store.add_reading`, `alarms.check`, `notify.process`); notes arrive via `_apply_event("note")`.
* Internal: all state lives in one process's memory with no persistence layer.
* Outbound: served back out through `/api/audit`, `/api/owners`, `/api/case`/`/api/history`, `/api/business`.

**Integration points:** Every other bucket reads from or writes to this store.

**Existing security controls:** None beyond the web-layer's host/origin checks gating read access.

**Identified gaps:** NFR-003 ("no single-store outage able to silently drop an audit or ownership record chain-wide") is not satisfiable by a single in-memory process — no persistence/replication design exists yet; NFR-005's redacted-identifier telemetry posture has no pipeline to enforce it against (NFR-008 defers the real OTel wiring); notes are stored and trusted with no integrity/provenance control.

### messaging

**Components:** `zava_cold_chain/notify.py` (alarm lifecycle, escalation, acknowledgement), `zava_cold_chain/alarms.py` (ALM-01/ALM-07 rule evaluation), the pager/escalation contact roster (`data/roster.json` `notify.contacts`).

**Data flows:**
* Inbound: alarm records raised by `alarms.check`.
* Internal: `notify.raise_alarm` → `_send` (per-contact, per-channel delivery attempt) → `process` (escalation after `escalate_after_minutes`, auto-acknowledgement simulation, corrective-action logging, clearing).
* Outbound: notifications to contact channels (app push, SMS, phone call) — simulated delivery status only (`"delivered"` / `"not delivered"`).

**Integration points:** Connects to `identity/auth`/`devops` (who is accountable for roster accuracy — "Pager contact list" owner, `data/roster.json`), `data` (alarm/incident records), `ai-ml` (FR-014's review-queue escalation reuses this same pattern).

**Existing security controls:** Escalation-after-timeout logic exists and is exercised by tests; every notification attempt (delivered or not) is logged to the live feed.

**Identified gaps:** A known-stale contact occupies an active level-1 escalation slot today (`roster.json`: `"refrigeration technician (left 2024)"`, `reachable: false` — ZFW-274, open); no recurring reachability-attestation cadence exists (FR-003 not yet implemented); a silent `"not delivered"` status has no operational alerting path of its own.

### infra

**Components:** Case controllers (physical refrigeration hardware, vendor-owned firmware — ZFW-319), the vendor remote-access channel's transport/session layer (as distinct from the identity bound to it), the store-network boundary the production rollout depends on.

**Data flows:**
* Inbound: vendor session open/close events, scripted/real commands reaching case controllers.
* Outbound: case temperature state flows back from controllers into the simulator's physics model (`PHYSICS` table) — a stand-in for a real sensor/controller link in production.

**Integration points:** `identity/auth` (vendor session identity), `devops/platform-ops` (firmware/patch ownership, contractually vendor-held).

**Existing security controls:** None described beyond the contractual vendor relationship.

**Identified gaps:** Case controller firmware is two versions behind (ZFW-319, backlog, vendor-contract-owned); no server-side enforcement of a vendor session's declared time-boxed window (today, open/close is purely event-driven with no expiry check); monitor does not measure elapsed defrost time independently of the command that started it (ZFW-188, open — a trust assumption on the controller, "not confirmed").

### devops/platform-ops

**Components:** Ownership register (`data/roster.json` "owners"), the Night Gauntlet evidence harness (`gauntlet.py`, FR-017/FR-018 gating), ZFW issue tracker entries that function as this system's informal backlog today.

**Data flows:** Ownership re-attestation (FR-016, not yet implemented) would flow owner-confirmation events into the register; gate results (`python -m zava_cold_chain gauntlet --seed 2026`) flow into cohort-expansion decisions (FR-017–FR-019).

**Integration points:** Every bucket's long-term accountability traces back here; the Night Gauntlet gate (FR-017/018) is the production rollout's single controlling checkpoint.

**Existing security controls:** The Gauntlet harness itself is a real, exercised evidence tool (confirmed in this session's PRD review); it is not, today, independently verified before a cohort-expansion decision.

**Identified gaps:** Two of seven in-scope system areas have **no active owner** today — "Fleet commands" (vacant since 2021) and "Store assistant" (vacant since 2024) (`data/roster.json`) — meaning the exact two components with the most severe findings in this plan (`commands.py`, `assistant.py`) have no accountable human reviewer in the organization right now; no independent-verification step is described for the self-run Gauntlet gate.

### ai-ml (included because `raiEnabled` is `true`)

**Components:** `zava_cold_chain/assistant.py` (`build_context`, `_model`, `STEER` regex, `ask`, `draft_discard_list`).

**Data flows:**
* Inbound: case state (mode/temperature/limit) plus every stored technician/vendor note for that case, concatenated verbatim into the answer-generation context.
* Internal: a keyword-pattern match (`STEER`) short-circuits to "Yes, the case is safe" if any note line matches an instructive-steering pattern; otherwise a simple mode/temperature-vs-limit comparison produces the answer.
* Outbound: the answer is returned to the caller and also emitted to the live feed (`w.emit("assistant", ...)`), visible to anyone with dashboard read access.

**Integration points:** Receives untrusted-by-design input from `messaging`/`infra` (the vendor portal, per ZFW-331, and the staff note channel) and from `identity/auth` (whichever account posted the note); its output reaches `web/UI/reporting` and, per FR-014, should feed a `messaging`-bucket review queue.

**Existing security controls:** The `STEER` regex is a real, working keyword-based guardrail stand-in — it is better than nothing, and it is exactly the kind of control a production LLM-backed assistant would need to replace with something more robust, not remove.

**Identified gaps:** This is the PRD's and this plan's single highest-severity bucket. See T-AI-001 through T-AI-004 in Phase 4.

### GS overlay (cross-cutting, applies to every bucket above)

Logging/monitoring (NFR-008, `telemetry-foundations`); incident response (alarm/incident/review-queue runbook currency, `docs`/`data/runbook.md`); compliance/evidence collection (Night Gauntlet record retention for FR-017/018); key management (future credential/token issuance for FR-006/FR-009, NFR-004's 60-minute revocation bar); security governance/exceptions (ZFW-203 and ZFW-305 are both recorded "won't fix" against a 5-store pilot threat model that the 400-store production rollout reopens); API security (rate limiting, connection caps on `server.py`).
